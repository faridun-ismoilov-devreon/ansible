# Архитектура ClickHouse кластера: Как это работает

## 📊 Ваша конфигурация

**Топология:** `1 shard × 3 replicas`

Это означает:
- **1 shard (шард)** - все данные хранятся в одном шарде (нет горизонтального разделения)
- **3 replicas (реплики)** - каждая запись реплицируется на все 3 ноды для отказоустойчивости

```
┌─────────────────────────────────────────────────────────┐
│                    ClickHouse Cluster                     │
│              production_cluster (1 shard)                │
├─────────────────────────────────────────────────────────┤
│                                                           │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐ │
│  │ ch-node-01   │  │ ch-node-02   │  │ ch-node-03   │ │
│  │ 192.168.150. │  │ 192.168.150. │  │ 192.168.150. │ │
│  │    140       │  │    141       │  │    142       │ │
│  │              │  │              │  │              │ │
│  │ Replica 01   │  │ Replica 02   │  │ Replica 03   │ │
│  │              │  │              │  │              │ │
│  │ [Данные]    │◄─┼─│ [Данные]    │◄─┼─│ [Данные]    │ │
│  │              │  │              │  │              │ │
│  │ 100% данных  │  │ 100% данных  │  │ 100% данных  │ │
│  └──────────────┘  └──────────────┘  └──────────────┘ │
│         │                  │                  │         │
│         └──────────────────┼──────────────────┘         │
│                            │                            │
│                    ┌───────▼────────┐                   │
│                    │  Keeper Cluster │                   │
│                    │  (3 ноды)       │                   │
│                    │  - keeper-01    │                   │
│                    │  - keeper-02    │                   │
│                    │  - keeper-03    │                   │
│                    └─────────────────┘                   │
└─────────────────────────────────────────────────────────┘
```

## 🔄 Как работает репликация

### 1. Запись данных (INSERT)

Когда вы вставляете данные в любую ноду:

```
Ваше приложение
    │
    ├─► INSERT INTO table VALUES (1, 'data')
    │
    ▼
┌─────────────┐
│ ch-node-01  │ ──┐
│ (любая)     │   │
└─────────────┘   │
                  │ Репликация через Keeper
                  │ (автоматически)
    ┌─────────────┼─────────────┐
    │             │             │
    ▼             ▼             ▼
┌─────────┐  ┌─────────┐  ┌─────────┐
│node-01  │  │node-02  │  │node-03  │
│[данные] │  │[данные] │  │[данные] │
└─────────┘  └─────────┘  └─────────┘
```

**Процесс:**
1. Вы отправляете INSERT на любую ноду (например, ch-node-01)
2. Нода записывает данные локально
3. Через Keeper нода уведомляет другие реплики
4. Другие реплики автоматически синхронизируют данные
5. Все 3 ноды теперь содержат одинаковые данные

### 2. Чтение данных (SELECT)

Вы можете читать с любой ноды - данные одинаковые:

```
Ваше приложение
    │
    ├─► SELECT * FROM table
    │
    ▼
┌─────────────┐
│ ch-node-01  │ ──► Всегда актуальные данные
│             │     (синхронизированы через Keeper)
└─────────────┘

ИЛИ

┌─────────────┐
│ ch-node-02  │ ──► Те же данные
└─────────────┘

ИЛИ

┌─────────────┐
│ ch-node-03  │ ──► Те же данные
└─────────────┘
```

## 🎯 Как должен работать ваш сервис

### Вариант 1: Подключение к одной ноде (простой)

```csharp
// Подключение к одной ноде
var host = "192.168.150.140"; // ch-node-01
var port = 8123;

// Все операции идут через эту ноду
// Репликация происходит автоматически на другие ноды
```

**Плюсы:**
- Простота
- Одна точка подключения

**Минусы:**
- Если эта нода упадет - сервис не работает
- Вся нагрузка на одну ноду

### Вариант 2: Балансировка между нодами (рекомендуется)

```csharp
public class ClickHouseClusterClient
{
    private readonly string[] _nodes = {
        "192.168.150.140",  // ch-node-01
        "192.168.150.141",  // ch-node-02
        "192.168.150.142"   // ch-node-03
    };
    
    private int _currentNodeIndex = 0;
    private readonly HttpClient _httpClient;
    
    // Round-robin балансировка
    private string GetNextNode()
    {
        var node = _nodes[_currentNodeIndex];
        _currentNodeIndex = (_currentNodeIndex + 1) % _nodes.Length;
        return node;
    }
    
    // Запись - можно на любую ноду
    public async Task InsertAsync(string query)
    {
        var node = GetNextNode();
        var url = $"http://{node}:8123/?query={Uri.EscapeDataString(query)}";
        await _httpClient.PostAsync(url, null);
        // Репликация произойдет автоматически!
    }
    
    // Чтение - можно с любой ноды
    public async Task<string> SelectAsync(string query)
    {
        var node = GetNextNode();
        var url = $"http://{node}:8123/?query={Uri.EscapeDataString(query)}";
        return await _httpClient.GetStringAsync(url);
    }
}
```

**Плюсы:**
- Распределение нагрузки
- Отказоустойчивость (если одна нода упадет, используем другие)
- Лучшая производительность

### Вариант 3: С retry и failover

```csharp
public async Task<string> ExecuteWithRetryAsync(string query)
{
    var exceptions = new List<Exception>();
    
    // Пробуем все ноды по очереди
    foreach (var node in _nodes)
    {
        try
        {
            var url = $"http://{node}:8123/?query={Uri.EscapeDataString(query)}";
            var response = await _httpClient.GetAsync(url);
            response.EnsureSuccessStatusCode();
            return await response.Content.ReadAsStringAsync();
        }
        catch (Exception ex)
        {
            exceptions.Add(ex);
            // Продолжаем на следующей ноде
            continue;
        }
    }
    
    // Если все ноды недоступны
    throw new AggregateException("All ClickHouse nodes unavailable", exceptions);
}
```

## 📝 Примеры работы

### Пример 1: Создание таблицы

```sql
-- Создается на ВСЕХ нодах одновременно
CREATE TABLE mydb.events ON CLUSTER production_cluster
(
    id UInt64,
    message String,
    timestamp DateTime DEFAULT now()
)
ENGINE = ReplicatedMergeTree('/clickhouse/tables/{shard}/mydb/events', '{replica}')
ORDER BY (timestamp, id);
```

**Что происходит:**
- Таблица создается на всех 3 нодах
- `{shard}` заменяется на `01` (у вас 1 shard)
- `{replica}` заменяется на `01`, `02`, `03` соответственно
- Keeper отслеживает метаданные таблицы

### Пример 2: Вставка данных

```sql
-- Вставляете на любую ноду
INSERT INTO mydb.events (id, message) VALUES (1, 'Hello');
```

**Что происходит:**
1. Данные записываются на ноду, куда вы отправили запрос
2. Через Keeper другие реплики узнают о новых данных
3. Реплики автоматически синхронизируются
4. Через несколько секунд данные доступны на всех нодах

### Пример 3: Чтение данных

```sql
-- Читаете с любой ноды - данные одинаковые
SELECT * FROM mydb.events;
```

**Что происходит:**
- Запрос обрабатывается локально на ноде
- Данные уже синхронизированы через репликацию
- Результат одинаковый на всех нодах

## 🔧 Роль Keeper

**Keeper** (аналог ZooKeeper) - это координатор кластера:

```
┌─────────────────────────────────────┐
│         Keeper Cluster              │
│  ┌─────────┐  ┌─────────┐  ┌──────┐│
│  │keeper-01│  │keeper-02│  │keeper││
│  │  143    │  │  144    │  │ -03  ││
│  └─────────┘  └─────────┘  └──────┘│
└─────────────────────────────────────┘
         │         │         │
         └─────────┼─────────┘
                   │
    ┌──────────────┼──────────────┐
    │              │              │
    ▼              ▼              ▼
┌─────────┐  ┌─────────┐  ┌─────────┐
│ch-node- │  │ch-node- │  │ch-node- │
│  01     │  │  02     │  │  03     │
└─────────┘  └─────────┘  └─────────┘
```

**Keeper отвечает за:**
1. **Метаданные таблиц** - где какая таблица находится
2. **Координация репликации** - синхронизация данных между репликами
3. **Leader election** - выбор ведущей реплики для операций
4. **Distributed DDL** - выполнение команд на всех нодах

## ⚡ Производительность и отказоустойчивость

### Отказоустойчивость

```
Нормальная работа:
┌──────┐  ┌──────┐  ┌──────┐
│Node 1│  │Node 2│  │Node 3│
│  ✅  │  │  ✅  │  │  ✅  │
└──────┘  └──────┘  └──────┘

Если Node 1 упала:
┌──────┐  ┌──────┐  ┌──────┐
│Node 1│  │Node 2│  │Node 3│
│  ❌  │  │  ✅  │  │  ✅  │
└──────┘  └──────┘  └──────┘
         ↑          ↑
    Ваш сервис может использовать любую из этих нод
```

**Минимальные требования:**
- Для чтения: достаточно 1 рабочей ноды
- Для записи: достаточно 1 рабочей ноды (репликация восстановится когда другие поднимутся)

### Производительность

**Чтение:**
- Можно распределить запросы между нодами (round-robin)
- Каждая нода обрабатывает запросы независимо
- Производительность = производительность одной ноды × количество нод (для чтения)

**Запись:**
- Запись идет на одну ноду
- Репликация происходит асинхронно (не блокирует запись)
- Производительность записи = производительность одной ноды

## 🎯 Рекомендации для вашего сервиса

### 1. Используйте балансировку

```csharp
// Хорошо ✅
var nodes = new[] { "192.168.150.140", "192.168.150.141", "192.168.150.142" };
var node = nodes[Random.Shared.Next(nodes.Length)];

// Плохо ❌
var node = "192.168.150.140"; // Только одна нода
```

### 2. Добавьте retry логику

```csharp
public async Task<T> ExecuteWithRetryAsync<T>(Func<string, Task<T>> operation)
{
    foreach (var node in _nodes)
    {
        try
        {
            return await operation(node);
        }
        catch (Exception ex)
        {
            // Log and try next node
            _logger.LogWarning($"Node {node} failed: {ex.Message}");
            continue;
        }
    }
    throw new Exception("All nodes failed");
}
```

### 3. Мониторинг нод

```csharp
public async Task<bool> IsNodeHealthyAsync(string node)
{
    try
    {
        var response = await _httpClient.GetAsync(
            $"http://{node}:8123/?query=SELECT+1", 
            cancellationToken: CancellationToken.None);
        return response.IsSuccessStatusCode;
    }
    catch
    {
        return false;
    }
}
```

### 4. Используйте ON CLUSTER для DDL операций

```sql
-- Создает на всех нодах автоматически

-- Вместо создания на каждой ноде отдельно ❌
```

## 📊 Сравнение: 1 shard × 3 replicas vs другие топологии

### Ваша конфигурация: 1 shard × 3 replicas

```
┌─────────────────────────────────────┐
│         Shard 01                     │
│  ┌──────┐  ┌──────┐  ┌──────┐      │
│  │Node 1│  │Node 2│  │Node 3│      │
│  │100%  │  │100%  │  │100%  │      │
│  └──────┘  └──────┘  └──────┘      │
└─────────────────────────────────────┘
```

**Характеристики:**
- ✅ Высокая отказоустойчивость (может потерять 2 ноды)
- ✅ Простота управления
- ❌ Нет горизонтального масштабирования (все данные на всех нодах)
- ❌ Ограничение по размеру = размер одной ноды

### Альтернатива: 3 shards × 2 replicas

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  Shard 1    │  │  Shard 2    │  │  Shard 3    │
│ ┌───┐ ┌───┐ │  │ ┌───┐ ┌───┐ │  │ ┌───┐ ┌───┐ │
│ │N1 │ │N2 │ │  │ │N2 │ │N3 │ │  │ │N3 │ │N1 │ │
│ │33%│ │33%│ │  │ │33%│ │33%│ │  │ │33%│ │33%│ │
│ └───┘ └───┘ │  │ └───┘ └───┘ │  │ └───┘ └───┘ │
└─────────────┘  └─────────────┘  └─────────────┘
```

**Характеристики:**
- ✅ Горизонтальное масштабирование (данные распределены)
- ✅ Больше общая емкость
- ❌ Сложнее управление
- ❌ Нужно больше нод
